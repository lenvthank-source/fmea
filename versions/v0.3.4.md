# v0.3.4 — 2026-08-27
## Summary
Resolves the production PFMEA batch import 500 error caused by unparseable date formats by introducing a resilient multi-format date parser (`parseFlexibleDate`) supporting `DD-MM-YYYY`, `DD/MM/YYYY`, `DD.MM.YYYY`, `YYYY-MM-DD`, and numeric Excel serial timestamps (e.g. `44804`) with safe `null` fallbacks. Adds dedicated separate and combined column mappings for Responsibility, Target Date, Action Taken, and Completion Date, and implements database sanitization guards for Action Priority (`@db.Char(1)`) and Severity/Occurrence/Detection ratings bounds.
## Changes
### Fixes
- **Multi-Format Date Parsing & Prisma Protection:** `backend/src/modules/pfmea/pfmea-row.service.ts:9,887` & `frontend/src/features/pfmea/components/PfmeaExcelImportWizard.tsx:233,741` implemented `parseFlexibleDate` and `formatDateIso` to convert day-first dates (`31-08-2022`), slash dates (`31/08/2022`), dot dates (`31.08.2022`), and Excel serial numbers (`44804`) into valid ISO Date objects, while returning `null` on unparseable text (`"TBD"`, `"Setting stop to be installed"`, empty) instead of an `Invalid Date` object, preventing PostgreSQL/Prisma runtime crashes.
- **Dedicated Responsibility & Date Column Mappings:** `frontend/src/features/pfmea/components/PfmeaExcelImportWizard.tsx:64,133,213,628` added separate column keys and synonyms for `responsibility`, `targetDate`, `actionTaken`, `completionDate` alongside combined keys (`responsibilityTargetDate`, `actionTakenCompletionDate`), preventing date extraction regex from clearing standalone responsibility names.
- **Production API URL Alignment:** `frontend/src/features/pfmea/components/PfmeaExcelImportWizard.tsx:45` replaced hardcoded localhost fallback with centralized `API_BASE_URL` from `config.ts` and integrated `parseApiError` from `lib/api.ts`.
### Refactors
- **Schema & Action Priority Sanitization:** `backend/src/modules/pfmea/pfmea-row.service.ts:58,867` added `sanitizeAp` to clamp action priority values to `'H' | 'M' | 'L' | null` to strictly enforce `@db.Char(1)` constraints, and clamped S/O/D ratings to the $[1, 10]$ range.
